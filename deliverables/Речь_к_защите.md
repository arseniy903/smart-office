## Слайд 1. Титульный слайд

Здравствуйте, уважаемые члены комиссии. Я представляю учебный проект «Умный офис» и практическую работу №6 — интеграцию базы данных SQLite.

## Слайд 2. О проекте

Цель проекта — прототип умного офиса, который следит за температурой и влажностью, управляет вентилятором серверной и хранит историю показаний. В работе №6 в систему добавлена база данных SQLite на виртуальной машине DB. Теперь показания датчиков и события вентилятора не только принимаются контроллером, но и сохраняются. Стенд развёрнут в GNS3 на РЕД ОС 8 и Windows Server 2019, сервисы запускаются через Docker Compose. Все три устройства — TEMP-01, HUM-01 и FAN-01 — имитируются в Node-RED.

## Слайд 3. Стенд в GNS3

На схеме видно, что стенд состоит из пяти рабочих узлов: WIN, CTRL, MON, DB и IOT. Маршрутизацию между VLAN 10, 20 и 30 выполняют Cisco RTR и Cisco SW. Вторым снимком на слайде открывается план офиса.

## Слайд 4. Адреса и сервисы

Адресация следующая. WIN — 192.168.10.10 в VLAN 10. DB — 192.168.20.10, MON — 192.168.20.11, CTRL — 192.168.20.12, все в VLAN 20. IOT — 192.168.30.10 в VLAN 30. Node-RED доступен на порту 1880, приёмник CTRL — на 8080, история показаний на DB — на 8081.

## Слайд 5. Как идут данные

Принцип работы. Датчики отправляют показания каждые пять секунд. Каждое сообщение датчика и каждое событие вентилятора уходит параллельно на два адреса: на CTRL и на DB. CTRL принимает данные и отдаёт метрики, DB сохраняет их в SQLite. Вентилятор включается командой ON при превышении порога температуры, иначе формируется OFF.

## Слайд 6. Две таблицы в базе

В базе две таблицы. measurements хранит показания: id, source, device_id, metric, zone, timestamp, received_at, value, unit и labels. actuator_events хранит события вентилятора: id, source, device_id, zone, timestamp, received_at, state и mode. Вторую таблицу я спроектировал самостоятельно, её структура соответствует состояниям ON и OFF и режиму auto.

## Слайд 7. Запуск сервиса хранения

Запуск сервиса. На DB установлены docker, docker compose и sqlite3. В папке practice-6 лежат compose.yml, server.py, index.html и inspect_db.py. База создаётся командой sqlite3 data/telemetry.sqlite3 < init.sql, затем выполняется docker compose up -d. Контейнер storage работает на порту 8081 с автозапуском restart: unless-stopped. Проверка health возвращает status ok, storage sqlite.

## Слайд 8. Поток в Node-RED

На слайде поток Node-RED. Для каждого датчика стоят два отдельных запроса: POST на CTRL и POST на DB. Сообщение уходит в оба сервиса. В Debug видно ответ от DB — status stored и идентификатор записи.

## Слайд 9. Проверка записи

Проверка записи. Страница истории на DB показывает последние значения HUM-01 и FAN-01, общее число записей и график. На снимках — страница истории, обновление данных и выборка SELECT из measurements. Дополнительно я проверял структуру actuator_events. Данные видны и в веб-интерфейсе, и через sqlite3.

## Возможные вопросы комиссии

**1. Почему для хранения выбрана SQLite, а не PostgreSQL?**

Стенд учебный, нагрузка небольшая. SQLite не требует отдельного сервера, хранится в одном файле и легко проверяется через sqlite3. Для промышленной системы с параллельной записью и большим объёмом данных выбрали бы PostgreSQL.

**2. Почему сервис не создаёт таблицы сам?**

По заданию база создаётся вручную до запуска контейнера. Проверка схемы при старте гарантирует, что сервис не начнёт писать в пустую или неправильную базу и не потеряет данные незаметно.

**3. Как обеспечивается параллельная отправка на CTRL и DB?**

В Node-RED после сборки сообщения стоят два независимых узла HTTP request: один отправляет POST на CTRL, второй — на DB. Они не зависят друг от друга, поэтому сообщение уходит в оба сервиса.

**4. Что произойдёт, если DB временно недоступна?**

Отправка на CTRL продолжится, а запись в DB не выполнится. Контейнер storage перезапустится автоматически, но пропущенные сообщения не восстанавливаются, потому что очереди в прототипе нет. Это ограничение учебной реализации.

**5. Чем подтверждается, что данные действительно сохраняются?**

Тремя способами: ответом сервиса status stored с идентификатором записи, веб-интерфейсом истории на порту 8081 и SQL-запросами к telemetry.sqlite3.

**6. Где хранится файл базы и почему его нет в репозитории?**

Файл лежит в подпапке data и подключён к контейнеру как том. В Git он не попадает, потому что база содержит изменяемые данные и исключена через .gitignore. В репозитории хранится только схема init.sql.
